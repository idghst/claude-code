# 팀 규칙 템플릿과 문서 작성 순서

에이전트는 사용자에게 팀 상황을 물은 뒤, 이 템플릿의 대괄호를 채워 `BRANCHING.md` 또는 `CONTRIBUTING.md` 초안을 만든다. 추측으로 채우지 않고, 모르는 칸은 질문하거나 `TBD`로 남긴다. 배포 주기나 QA 방식이 바뀌면 문서도 함께 수정한다.

## 작성 순서

1. 선택한 전략 이름과, 그 전략을 고른 이유를 한 문단으로 적는다.
2. 아래 필수 항목을 모두 채운다.
3. 브랜치 이름, 커밋 메시지, PR/MR, 보호 브랜치, 태그, 핫픽스 절차를 적는다.
4. 초안을 보여 주고, 사용자가 확인한 뒤에만 저장소에 파일을 만든다.
5. 파일 이름은 팀이 이미 `CONTRIBUTING.md`를 쓰면 그 안에 브랜치 절을 넣거나, 별도 `BRANCHING.md`를 만들고 `CONTRIBUTING.md`에서 링크한다.

## 필수 항목

이 일곱 가지는 빠뜨리지 않는다.

| 항목 | 값 |
| --- | --- |
| 배포 브랜치 | [예: `main` / `production`] |
| 작업 시작 브랜치 | [예: `develop` / `main`] |
| 최대 브랜치 수명 | [예: 2일 / 릴리스 주기 안] |
| QA 수정이 들어가는 위치 | [예: `release/*` / 작업 브랜치 / `main`] |
| hotfix를 추가로 반영하는 위치 | [예: `develop`와 열린 `release/*` / `main`(당일 cherry-pick)] |
| 병합 권한자 | [예: 리뷰어 1명 승인 후 작성자 / 유지보수 팀만] |
| 병합 후 브랜치 삭제 | [예: 원격·로컬 모두 삭제 / 릴리스 브랜치는 유지] |

## 초안 템플릿

아래를 복사해 대괄호를 채운다.

```markdown
# 브랜치·배포 규칙

이 저장소는 **[전략 이름]** 을 따른다. [한 줄 이유: 배포 주기, QA, 환경 분리].

## 핵심 규칙

- 배포 브랜치: `[브랜치]`
- 작업 시작 브랜치: `[브랜치]`
- 최대 브랜치 수명: `[기간]`
- QA 수정 위치: `[브랜치]`
- hotfix 추가 반영 위치: `[브랜치 목록]`
- 병합 권한자: `[역할 또는 인원]`
- 병합 후 브랜치 삭제: `[예/아니오, 예외]`

## 브랜치 이름

- 기능: `feature/<이슈번호>-<짧은-설명>`
- 버그: `bugfix/<이슈번호>-<짧은-설명>`
- 릴리스: `release/<major.minor.patch>` (쓰는 전략만)
- 핫픽스: `hotfix/<major.minor.patch-또는-이슈>` (쓰는 전략만)
- 설명은 소문자와 하이픈만 쓰고, 공백·슬래시 연속은 쓰지 않는다.

## 커밋 메시지

- 제목은 50~72자 안으로, 명령형으로 쓴다.
- [Conventional Commits를 쓰는 경우] `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:` 접두어를 붙인다.
- 본문에는 이유와 영향 범위를 적는다. 이슈 번호는 제목 또는 본문에 남긴다.

## Pull / Merge Request

- 기본 대상 브랜치: `[develop 또는 main]`
- 필수 리뷰어 수: `[N]`명. CI(테스트·린트)가 통과해야 병합할 수 있다.
- 병합 방식: `[Merge commit / Squash / Rebase]` 하나를 팀 전체에서 동일하게 쓴다.
- 설명에는 변경 요약, 테스트 방법, 관련 이슈를 적는다.
- 자가 병합이 가능한지: `[예/아니오]`

## 보호 브랜치

- 보호 대상: `[main, develop, production, release/* 등]`
- 직접 push는 금지하고, PR/MR만 허용한다.
- 필수 상태 검사: `[테스트 Job 이름]`
- force push와 이력 재작성은 금지한다. 예외가 있으면 여기에만 적는다.

## 태그 / 버전

- 형식: `vMAJOR.MINOR.PATCH` (Semantic Versioning)
- 태그를 다는 시점: `[main 또는 production 병합 직후]`
- 누가 태그를 다는지: `[CI / 릴리스 담당]`
- 태그가 배포를 트리거하는지: `[예/아니오]`

## 핫픽스 절차

1. `[시작 브랜치]`에서 `hotfix/...`를 분기한다.
2. 최소 수정만 넣고, 리뷰와 테스트를 통과시킨다.
3. `[배포 브랜치]`에 병합하고 태그를 올린 뒤 배포한다.
4. 반드시 `[추가 반영 위치]`에도 같은 수정을 넣는다. 빠진 곳이 있으면 다음 배포에서 버그가 되살아난다.
5. 핫픽스 브랜치를 삭제한다.

## 예외

- [긴급 배포, 문서만 변경, 실험 브랜치 등 예외가 있으면 적는다. 없으면 "없음"]
```

## 전략별로 자주 채우는 값

값을 강요하지 말고, 팀 대답이 없을 때만 출발점으로 제안한다.

- **Git Flow:** 작업 시작은 `develop`, 배포는 `main`, QA 수정은 `release/*`, hotfix는 `main`·`develop`·열린 `release/*`, 브랜치 수명은 릴리스 주기 안.
- **GitHub Flow:** 작업 시작과 배포는 모두 `main`, QA 수정도 작업 브랜치, hotfix도 같은 경로, 최대 수명은 하루~이틀, 병합 후 브랜치 삭제.
- **GitLab Flow (환경형):** 작업 시작은 `main`, 배포는 `production`, QA는 `staging`, 운영 수정은 당일 `main`으로 cherry-pick, 환경 브랜치는 앞방향만.
- **GitLab Flow (버전형):** `release/x.y`에는 cherry-pick만. 기능 추가 금지.
- **Trunk-Based:** 작업 시작과 배포는 `main`, 최대 수명 1~2일, 활성 브랜치 3개 이하, 미완성은 flag, 릴리스 브랜치를 쓰면 스냅샷만, 그 수정은 즉시 trunk로.
